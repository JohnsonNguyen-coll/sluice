# x402 compatibility

Sluice managed APIs expose two payment transports for the same JSON service:

- `/hosted/:serviceId` uses AgentPay vouchers, signed receipts, spending
  policies, negotiation and the V3 dispute vault.
- `/x402/:serviceId` uses x402 v2 `batch-settlement` on Arc Testnet. It is for
  clients that already speak the standard x402 HTTP protocol.

These are separate payment rails. An x402 payment does not automatically gain
an AgentPay receipt or a claim in `NegotiationDisputeVault`.

## Result delivery and payment ordering

An unpaid x402 request receives HTTP 402 and the standard
`PAYMENT-REQUIRED` header. The request handler is not executed.

On retry, Sluice reads `PAYMENT-SIGNATURE`, verifies the deposit or cumulative
voucher, and only then calls the provider's upstream API. For a successful
upstream response, Sluice commits the voucher before releasing the JSON body.
If commitment fails, the successful body is withheld and the caller receives
HTTP 402 with a settlement failure. Failed upstream responses invoke the x402
cancellation path and are not treated as a successful paid result.

The result is delivered to the caller in the normal HTTP response body:

```ts
const response = await paidFetch(endpoint, {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify(input),
});
const result = await response.json();
```

The provider dashboard shows endpoints and settlement state. It does not
publish or persist private API response bodies.

## Escrow and settlement worker

The x402 batch-settlement contract escrows the caller's USDC. Subsequent calls
use cumulative off-chain vouchers. Sluice persists channel state and pending
deposit transaction hashes under the ignored `.tools/x402/` directory locally
or `X402_STORAGE_DIR` on a production volume. The existing
managed-provider lease prevents x402 transactions from racing AgentPay
settlement transactions that use the same operational signer.

Every worker cycle checks for claimable x402 vouchers, batches claims and
settles claimed USDC to the provider's payout wallet. A provider cannot serve a
successful result before payment verification, and a caller cannot revoke a
signed cumulative claim merely because the on-chain batch runs later.

The supported Railway deployment uses one backend replica and a persistent
volume. A multi-instance deployment needs a shared transactional channel store
and shared deposit reconciliation before horizontal scaling. Pending hashes are
persisted on the volume, but a lost transaction or stale channel still needs
operator reconciliation against chain state.

On 2026-11-01, `contract/scripts/x402-testnet-e2e.ts` exercised a paid call
against the same external, read-only JSON API: unpaid 402, paid 200 with a
`PAYMENT-RESPONSE` header, followed by a worker settlement transaction. The
public report is `contract/deployments/x402-testnet-e2e.json`. This does not
exercise a provider's private credential or a Railway volume restart.
